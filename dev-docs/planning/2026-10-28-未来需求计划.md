## 一、外部审查结论与本地验证（2026-10-28）

外部审查提出 5 个技术问题，逐条本地验证结果如下：

| # | 问题 | 级别 | 验证结论 | 处置 |
|---|---|---|---|---|
| 1 | scene-builder 全局 compCache + buildChildren 直接改写缓存节点，循环引用时写入的 unsupported 会残留到不同入口的后续构建 | P0 | **属实**。node.childComp / node.unsupported 直接 mutate 缓存内对象 | 阶段 A：构建产物与缓存分离，构建生成新对象 |
| 2 | getComponent 缓存永不失效，XML 修改后服务化场景下刷新无效 | P0 | **属实**（当前 CLI 每次新进程未暴露，服务化后必现） | 阶段 A/B：服务化第一版每次请求重新解析，后续按 mtime/内容哈希失效 |
| 3 | data-fgui-path 按 name 拼接，同层同名节点路径重复，不保证唯一 | P1 | **属实**（FairyGUI 中 id 唯一但 name 可重复） | 阶段 A：保留可读路径用于搜索，新增稳定定位键（资源 id + 节点 id + 层级） |
| 4 | displayList 用 Object.entries 处理，fast-xml-parser 默认按标签聚合，混排顺序丢失 | P1（实际严重度 P0） | **属实，且是真实潜伏 bug**：`image,text,image` 会渲染成全部 image 在前 text 在后，z 序错误。此前样本节点位置不重叠未暴露 | **阶段 A 首要任务**：改用 preserveOrder 模式或有序解析，补混排 z 序回归断言 |
| 5 | 测试只验 HTML 字符串，不验视觉一致性 | P2 | 属实 | 阶段 E：Playwright 截图视觉回归，逐步建标准样本 |

文档一致性修正：P1-执行报告状态行已同步为「验收通过」（此前滞后于进度表）。

## 二、推荐开发路线（阶段 A-E）

### 阶段 A：修正核心数据结构（最优先）

**目标**：建立可靠的 Scene Tree 数据模型，解决四个基础正确性问题。

| 任务 | 内容 |
|---|---|
| A1 | displayList 有序解析：保留 XML 原始混排顺序（z 序正确性），补 image/text 交错回归断言 |
| A2 | 构建与缓存分离：parse 结果不可变，buildChildren 每次生成新 Scene Tree；补「重复构建 / 不同入口 / 循环引用」回归测试 |
| A3 | 唯一实例标识：保留可读 path 供搜索，新增稳定键（pkgId + 资源 id + 节点 id + 层级序号），区分同资源多实例与同名节点 |
| A4 | 缓存失效策略接口：为阶段 B 预留（请求级重解析起步） |

**验收**：check 断言覆盖混排 z 序、重复构建幂等、循环引用隔离、唯一键稳定性；BagWin / Demo_Image 回归不退化。

### 阶段 B：只读工作区服务

**目标**：Node 服务读取本地工程，网页端导航浏览，不再手动跑脚本。

- 工程根配置 + 路径边界校验（拒绝目录穿越，只允许配置根内访问）
- 包/组件枚举接口；按需解析（每请求重解析起步，衔接 A4）
- Scene Tree JSON 接口（AI 与前端共用的核心数据模型）+ 资源静态服务
- 明确不做：项目导入、保存、写回、云存储（保持只读）

**验收**：浏览器三级导航（工程 → 包 → 组件）；越界请求被拒；改 XML 后刷新生效。

### 阶段 C：搜索与画布定位

**目标**：名称 / ID / 路径检索 → 多结果选择 → 高亮 + 滚动定位。

- 构建时生成轻量索引（基于 A3 唯一键 + 可读 path）
- 搜索框 + 结果列表 + 上下切换；父链展开、滚动到可视区、外发光高亮

**验收**：搜索 closeButton 命中嵌套三层节点；同名节点可切换；命中节点滚入视口。

### 阶段 D：MCP 与 AI 联动

**目标**：AI 搜索真实组件 → 打开画布高亮 → 截图自验，完成最小闭环：

> 用户：「帮我找到背包里的头像框」→ AI 搜索工程 → 定位实例 → 画布高亮 → 返回节点信息与截图

**工具草案**（render_component 返回 HTML 地址 + 结构化节点信息，不只文件路径）：

| 工具 | 输入 | 输出 |
|---|---|---|
| list_components | 工程根 + 包名 | 组件清单（含唯一键、可读路径、扩展类型） |
| locate_component | 名称/ID 模糊匹配 | 唯一键 + 可读路径列表 |
| render_component | 唯一键 | 预览 URL + 结构化节点信息（bounds 用设计坐标） |
| screenshot_component | 唯一键 + 视口 | PNG 截图（无头浏览器，届时选型 Playwright/CDP） |

**坐标约定**：Scene Tree 提供 FairyGUI 设计坐标；浏览器实际显示坐标由 DOM 布局测量获得，两套不混用。

**验收**：三类场景覆盖——同名组件重复出现、嵌套三层以上、修改 XML 后重新定位。

### 阶段 E：按需提升视觉还原度

- 触发方式：以真实工程的未支持清单与截图差异驱动，不批量铺开
- 候选项（优先级从高到低）：跨包引用（`ui://pkgId+resId`，需工程级资源索引）→ fork 格式兼容（fileName 扩展）→ ComboBox/ProgressBar 等扩展组件 → graph 描边/多边形（SVG 混合）→ movieclip 首帧
- 附加：Playwright 截图视觉回归，逐步固化标准样本
- 明确排除：动画播放、完整交互运行时（目标 B，不追求 100% 还原）

## 三、核心架构原则（审查采纳）

1. **Scene Tree 是核心数据模型**：浏览器点选、搜索、MCP 调用共用同一份结构化节点信息，HTML 只是渲染产物
2. **本地工程为唯一数据源**：只读、不复制工程（无 OPFS/IndexedDB）
3. **区分「渲染错误」与「未实现」**：未支持清单机制持续保留
4. **从验证渲染技术转向验证 AI 能否准确找到真实组件**：阶段 D 的最小闭环是下一里程碑
