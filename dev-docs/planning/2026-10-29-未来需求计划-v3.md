# fairygui-html-renderer 未来需求计划（v3：双向转换路线图）

- 原计划日期：2026-10-28；本次修订：2026-10-29（v3）
- v3 定位：先完成 FairyGUI XML → HTML，再探索 HTML/React → FairyGUI XML，最终支持 AI 驱动的 FairyGUI UI 创建与修改
- v1 原四方向：工作区集成 / MCP 工具化 / 搜索高亮 / 格式补全
- 状态：规划（未排期）。A–E 沿用 v2 既有路线；F–H 为未来新阶段，均未宣称可行性已经验证。启动任一阶段前，先按项目规范拆解为独立执行计划

## 补充探查项（2026-10-29 审阅时新增）

1. **阶段 F 前置**：FairyGUI 编辑器打开工程需要完整工程骨架（.fairy 工程文件 + package.xml + settings），F4/F5 前应先探明 .fairy 文件格式（XML 还是二进制）——CC-Default 的 `FairyGUI-cocoscreator-demo.fairy` 是现成样本；若为私有二进制格式，则需评估以「最小可打开工程」为目标逆向骨架或改用编辑器插件写入路径
2. **阶段 G 反向映射机会**：CSS `border-image-slice/width` 可确定性反推九宫格 `scale9grid` 参数——HTML 侧使用 border-image 的节点写回时可恢复为原生九宫格属性而非烘焙，提高可编辑性占比，建议纳入 style-mapper 规则集

## 一、外部审查结论与本地验证（2026-10-28）

外部审查提出 5 个技术问题，逐条本地验证结果如下：

| # | 问题 | 级别 | 验证结论 | 处置 |
|---|---|---|---|---|
| 1 | scene-builder 全局 compCache + buildChildren 直接改写缓存节点，循环引用时写入的 unsupported 会残留到不同入口的后续构建 | P0 | **属实**。node.childComp / node.unsupported 直接 mutate 缓存内对象 | 阶段 A：构建产物与缓存分离，构建生成新对象 |
| 2 | getComponent 缓存永不失效，XML 修改后服务化场景下刷新无效 | P0 | **属实**（当前 CLI 每次新进程未暴露，服务化后必现） | 阶段 A/B：服务化第一版每次请求重新解析，后续按 mtime/内容哈希失效 |
| 3 | data-fgui-path 按 name 拼接，同层同名节点路径重复，不保证唯一 | P1 | **属实**（FairyGUI 中 id 唯一但 name 可重复） | 阶段 A：保留可读路径用于搜索，新增稳定定位键（资源 id + 节点 id + 层级） |
| 4 | displayList 用 Object.entries 处理，fast-xml-parser 默认按标签聚合，混排顺序丢失 | P1（实际严重度 P0） | **属实，且是真实潜伏 bug**：`image,text,image` 会渲染成全部 image 在前 text 在后，z 序错误。此前样本节点位置不重叠未暴露 | **阶段 A 首要任务**：改用 preserveOrder 模式或有序解析，补混排 z 序回归断言 |
| 5 | 测试只验 HTML 字符串，不验视觉一致性 | P2 | 属实 | 阶段 E：Playwright 截图视觉回归，逐步建标准样本 |

文档一致性修正：P1-执行报告状态行已同步为「验收通过」（此前滞后于进度表）。

## 二、推荐开发路线（阶段 A-E）

### 阶段 A：修正核心数据结构（最优先）

**目标**：建立可靠的 Scene Tree 数据模型，解决四个基础正确性问题。

| 任务 | 内容 |
|---|---|
| A1 | displayList 有序解析：保留 XML 原始混排顺序（z 序正确性），补 image/text 交错回归断言 |
| A2 | 构建与缓存分离：parse 结果不可变，buildChildren 每次生成新 Scene Tree；补「重复构建 / 不同入口 / 循环引用」回归测试 |
| A3 | 唯一实例标识：保留可读 path 供搜索，新增稳定键（pkgId + 资源 id + 节点 id + 层级序号），区分同资源多实例与同名节点 |
| A4 | 缓存失效策略接口：为阶段 B 预留（请求级重解析起步） |

**验收**：check 断言覆盖混排 z 序、重复构建幂等、循环引用隔离、唯一键稳定性；BagWin / Demo_Image 回归不退化。

### 阶段 B：只读工作区服务

**目标**：Node 服务读取本地工程，网页端导航浏览，不再手动跑脚本。

- 工程根配置 + 路径边界校验（拒绝目录穿越，只允许配置根内访问）
- 包/组件枚举接口；按需解析（每请求重解析起步，衔接 A4）
- Scene Tree JSON 接口（AI 与前端共用的核心数据模型）+ 资源静态服务
- 明确不做：项目导入、保存、写回、云存储（保持只读）

**验收**：浏览器三级导航（工程 → 包 → 组件）；越界请求被拒；改 XML 后刷新生效。

### 阶段 C：搜索与画布定位

**目标**：名称 / ID / 路径检索 → 多结果选择 → 高亮 + 滚动定位。

- 构建时生成轻量索引（基于 A3 唯一键 + 可读 path）
- 搜索框 + 结果列表 + 上下切换；父链展开、滚动到可视区、外发光高亮

**验收**：搜索 closeButton 命中嵌套三层节点；同名节点可切换；命中节点滚入视口。

### 阶段 D：MCP 与 AI 联动

**目标**：AI 搜索真实组件 → 打开画布高亮 → 截图自验，完成最小闭环：

> 用户：「帮我找到背包里的头像框」→ AI 搜索工程 → 定位实例 → 画布高亮 → 返回节点信息与截图

**工具草案**（render_component 返回 HTML 地址 + 结构化节点信息，不只文件路径）：

| 工具 | 输入 | 输出 |
|---|---|---|
| list_components | 工程根 + 包名 | 组件清单（含唯一键、可读路径、扩展类型） |
| locate_component | 名称/ID 模糊匹配 | 唯一键 + 可读路径列表 |
| render_component | 唯一键 | 预览 URL + 结构化节点信息（bounds 用设计坐标） |
| screenshot_component | 唯一键 + 视口 | PNG 截图（无头浏览器，届时选型 Playwright/CDP） |

**坐标约定**：Scene Tree 提供 FairyGUI 设计坐标；浏览器实际显示坐标由 DOM 布局测量获得，两套不混用。

**验收**：三类场景覆盖——同名组件重复出现、嵌套三层以上、修改 XML 后重新定位。

### 阶段 E：按需提升视觉还原度

- 触发方式：以真实工程的未支持清单与截图差异驱动，不批量铺开
- 候选项（优先级从高到低）：跨包引用（`ui://pkgId+resId`，需工程级资源索引）→ fork 格式兼容（fileName 扩展）→ ComboBox/ProgressBar 等扩展组件 → graph 描边/多边形（SVG 混合）→ movieclip 首帧
- 附加：Playwright 截图视觉回归，逐步固化标准样本
- 明确排除：动画播放、完整交互运行时（目标 B，不追求 100% 还原）


## 三、双向转换的长期目标（v3 新增）

### 总体定位

本仓库逐步从单向 `fairygui-html-renderer` 演进为 **FairyGUI ↔ HTML/React 双向 UI 桥接能力**，最终服务于 AI 游戏 UI 开发工作区。

- **第一条链路（当前 A–E）**：FairyGUI XML + 资源 → Parser / Scene Tree → HTML 预览、节点搜索定位、MCP、截图验证。
- **第二条链路（未来 F–G）**：需求 → AI 生成 HTML/React → 浏览器运行、预览、修改 → DOM/CSS/资源提取 → 确定性转换 → FairyGUI XML + 资源 → 编辑器打开。
- **最终闭环（未来 H）**：AI 创建或修改 UI，转换前后通过结构检查、截图和真实 FairyGUI 编辑器验证。

**重要约束**：AI 优先使用成熟的 HTML/React/CSS 能力生成 UI，**不再以要求大模型生成自定义 FairyGUI DSL JSON 为主要技术路线**。可以由程序生成 DOM Snapshot/内部 JSON 作为转换传输数据，但不能把它变成另一套需要模型学习的生成语言。

### 阶段 F：HTML → FairyGUI XML 最小可行性 POC（第二条链路的第一个门槛）

**目标**：验证一个真实浏览器中的简单 HTML 页面能否被转换为 FairyGUI 编辑器可打开、可选中、可继续编辑和保存的原生组件；本阶段不开发完整 UI 工作台。

| 任务 | 内容 |
|---|---|
| F1 | 选择最小样本：固定画布尺寸，包含容器、文本、图片、基本背景；保留嵌套、覆盖顺序和有意义的节点名称 |
| F2 | Playwright/Chromium 加载 HTML，提取 DOM 树、getBoundingClientRect、Computed Style、图片引用和文本；正确换算视口到画布坐标 |
| F3 | 制作确定性映射：容器 → component、文本 → text、图片 → image；先支持静态布局与原生可编辑节点，Flex/Grid 只导出浏览器计算后的最终位置 |
| F4 | 基于真实 FairyGUI 原版 XML 样本实现独立 XML Writer，处理 package.xml 资源登记、ID/文件名分配、图片复制与引用完整性 |
| F5 | 先输出到隔离测试包/临时工程，验证 FairyGUI 编辑器能打开、选中、修改、保存；禁止直接覆盖现有生产包 |
| F6 | 用当前 XML → HTML 渲染器回读，再做 DOM 节点检查和浏览器截图比较；以真实编辑器打开与保存结果作为最终验收 |

**本阶段明确不做**：复杂 React 状态/事件、动态动画、响应式行为还原、全部 CSS 特性支持、现有 FairyGUI 组件自动复用、复杂现有工程写回。

**验收门槛**：至少一套非截图平铺的示例 UI 能转换并在 FairyGUI 编辑器打开、独立编辑文本/图片/容器、保存后再次打开；资源引用完整、无重复 ID、节点基本顺序与坐标正确；明确列出未支持样式及降级结果。任何一项不通过，不进入 G 的全面开发。

**重要技术风险**：HTML 和 FairyGUI 的布局/视觉/交互语义并不完全等价；浏览器算得出静态坐标不代表能保留响应式布局或 React 业务逻辑。导出需支持原生映射、局部资源烘焙与不支持报告三种处理方式。不能把整个页面烘焙为一张图片后宣称转换成功。

### 阶段 G：HTML/React → FairyGUI 可重复转换流水线

**前置条件**：阶段 F 验收通过，并识别出实际的转换覆盖范围。

**目标**：输入 HTML 文件、预览 URL 或 React 构建产物，稳定输出 FairyGUI 组件 XML 和相关资源；支持 AI 先生成 React，再在浏览器中调试后导出。

- 独立模块：`browser-extractor`（页面与 DOM 快照）→ `style-mapper`（CSS 转换规则）→ `asset-pipeline`（图片与局部效果处理）→ `fairygui-writer`（XML 与资源登记）→ `validator`（回读和比较）。这些是建议职责，不要求立即采用对应目录名。
- 原生转换优先：文本、图片、容器、层级、绝对位置、尺寸、透明度、部分旋转等；复杂阴影/渐变/SVG 等视情况局部烘焙；无法表达的动态特性明确告警。
- React 可以自由承担设计与预览；导出发生在实际浏览器渲染之后，不通过静态解析 JSX 计算布局。
- 输出包含转换报告：节点总数、原生转换数、烘焙数、未支持数、资源清单、视觉差异与验证结果。
- 确保重复导出稳定且资源 ID 不冲突；生成结果优先写入隔离目录，通过校验和明确审批后才考虑写回既有 FairyGUI 工程。
- 扩展测试样本：文本图片组合 → Flex/Grid 背包界面 → 含复杂视觉效果的游戏 UI，逐项明确视觉保真和可编辑性的权衡。

**验收**：多个样本在真实 FairyGUI 编辑器中可打开、编辑和保存；导出结果可重复、资源完整；自动回归覆盖节点层级、坐标、遮挡顺序与截图差异；超出支持范围时产生可靠诊断而非静默错误。

### 阶段 H：AI 游戏 UI 工作区（长期目标）

**前置条件**：A–D 的读取/定位链路与 G 的写出链路均可稳定使用。

**目标场景**：用户描述“生成背包界面”→ AI 生成 React/HTML → 浏览器查看/修改 → 转 FairyGUI → 用户验收；以及用户描述“修改当前背包头像框下的数量文字”→ 定位现有组件 → 修改候选 UI → 导出局部变更 → 验证后写回。

- 先支持**新建 UI**，再探索**修改既有 UI**；修改必须保留未变更节点的稳定 ID、资源引用和层级，不能通过无差别重建覆盖原工程。
- 复用阶段 C/D 的组件搜索、定位与截图能力；后续可增加基于 `ui://` 的现有组件复用推荐。
- 写回采用显式审批、差异预览、备份/回滚和工程级锁；读取服务的默认只读边界继续保留，写入由独立受控接口承担。
- 核心评价指标：成功打开率、原生可编辑节点占比、视觉差异、人工修复时间、重生成稳定性，而不是“AI 一次写出了多少 JSX”。

**验收**：至少完成一套新建 UI 的端到端闭环，以及一套不破坏无关节点的现有 UI 小范围修改闭环，并通过人工在 FairyGUI 编辑器中验收。

## 四、阶段衔接、依赖与优先级（v3 新增）

1. **当前主线仍为 A → B → C → D；E 按真实问题穿插**。不要为了未来的写出能力提前重构当前读取端，也不要开发完整在线编辑器。
2. **F 是一个有意隔离的技术验证**：待第一阶段基本可用后，可以独立启动；无需等 E 所有格式补全做完，但需要至少具备能回读 F 产物的基础能力。
3. **F 通过才启动 G；G 的转换稳定后再启动 H**。F 如果发现原版 FairyGUI XML 写回成本过高，可以评估编辑器插件写入作为替代落地路径，不能把其可行性视作既定事实。
4. 第一阶段为第二阶段保留可复用的测试样本、节点 ID 约定、资源索引和视觉回归能力，但**不强制共用单一 IR**：`Scene Tree` 是 FairyGUI 读取侧模型，`DOM Snapshot` 是浏览器提取侧模型，转换器内部可以使用受限结构化数据。
5. 第一阶段“本地工程唯一数据源、默认只读”继续有效；第二阶段才引入**隔离的、需要审批的写出流程**，两者安全边界不可混淆。

## 五、核心架构原则（整合 v2 + v3）

1. **读取侧 Scene Tree 是核心数据模型**：浏览器点选、搜索、MCP 调用共用同一份结构化节点信息；HTML 是读取侧渲染产物。
2. **生成侧以 HTML/React 为设计源**：AI 使用成熟 Web 前端能力产出 UI，浏览器运行后提取 DOM、Computed Style 和资源，再由程序规则转换为 FairyGUI；无需 AI 生成 FairyGUI DSL。
3. **本地工程为唯一权威来源，读取默认只读**：不引入 OPFS/IndexedDB 工程副本；未来写入必须独立隔离、预览和审批。
4. **严格区分不支持、渲染错误、转换降级和数据损坏**：读取与写出均产生可追踪报告。
5. **可编辑性优先于截图相似**：能映射为 FairyGUI 原生组件时不应整屏烘焙；局部烘焙需明确标注编辑性损失。
6. **双向验证不等于完全无损双向转换**：HTML/CSS 与 FairyGUI 的状态、布局、动画能力不同；以明确的支持子集和真实编辑器验收为准。
7. **短期目标是准确读取、定位 UI，长期目标是 AI 创建与修改 FairyGUI UI**。
