# egret-exml-html-renderer 对比分析：需同步到本项目的部分

> 日期：2026-11-05
> 对象：姊妹项目 `E:/DesignProjects/egret-exml-html-renderer`（Egret EXML 静态渲染器，后建项目，基础设施沿袭本项目早期规则后又长出了一整层能力）
> 结论先行：**对方比我们多出"AI 工作台基础设施"一整层（P2/P3/P4 三期）**，本项目目前只有渲染 + 简单导航页。按价值排序共识别 8 项可同步、3 项不可同步、2 项反向同步。

## 一、两个项目的能力对照总表

| 能力层 | fairygui-html-renderer（本项目） | egret-exml-html-renderer | 差距 |
|--------|------|------|------|
| 渲染核心 | 15 节点/扩展分支 + gear + jta 播放 + BMFont + 树 | 9 节点文件（引擎差异） | 各自对齐各引擎，不可比 |
| Scene JSON | `/api/scene`（含 relativize） | 同 + nodeDetail/findNodeByKey | 基本对齐 |
| 全局索引 | global-index（pkg -> resources，ui:// 解析） | ui-asset-index（三层元数据：基础/结构/资源 + 解析失败诊断） | **对方厚一层** |
| 搜索 | `/api/search`（name/id/路径） | searchUiAssets + findComponentUsages（**反向引用查询**） | **对方多引用关系** |
| 组件关系图谱 | 无（只有场景级循环引用检测 onCycle） | component-graph（引用边三类 / Tarjan SCC 环 / 出入度 / 枢纽排行 / 孤儿报告） | **完全缺失** |
| 场景 diff | 无 | scene-diff（added/removed/moved/changed 属性级，id 主键 + 顺序配对两层身份） | **完全缺失** |
| HTML -> XML 写出 | 无 | exml-writer（语义 HTML -> EXML，装饰节点跳过，无语义报错不静默） | **完全缺失** |
| 工作台页面 | 三级导航 + iframe（无选择联动） | **三栏可视化编辑器**：工程树 + Scene Tree + Canvas + Inspector + 缩放 + 关系条 + postMessage 双向选中同步 | **差距最大的一块** |
| MCP 工具 | 4 个（list/locate/render/screenshot） | 9 个（多 scene 详情/搜索/引用/图谱/diff/写出） | 差 5 个 |
| 路径守卫 | safeResolve（前缀检查） | safeResolveWithin（**+ 符号链接 realpath 复核**） | 对方多一层 |
| 测试体系 | render/server/convert/mcp 四套件 | 8 套件（多 ui-asset/graph/diff/writer） | 随功能走 |
| AI 验证方法 | 无 | benchmark 体系（Gate A 理解 / Gate B 修改 两门评测 + ground-truth + 程序化评分） | 方法论可借 |
| 读者向文档 | docs/（6 篇 + zh-CN） | docs/（5 篇） | 对齐 |

## 二、需要同步的部分（按价值排序）

### S1. 三栏可视化工作台（最高优先级）

对方 `src/editor/`（约 1170 行，五个模块）：左栏（工程树 + Scene Tree 上下分区）/ 中栏（关系条 + Canvas iframe）/ 右栏（Inspector 属性检查器），拖拽分隔条、缩放、postMessage 双向选中同步（点画布节点 -> 树定位 -> Inspector 显示属性）。

本项目现状：`index-html.ts` 只有 100 行的三级导航 + 裸 iframe。

- **为什么值得**：本项目的主线正是《UI 工作台接入需求文档》（dev-docs/planning/2026-10-29），工作台 P0 就是这套东西。对方已趟完 P3-A 三期（页面骨架 -> 选中同步 -> Inspector），踩坑文档齐全。
- **同步方式**：结构照搬（五个模块的职责划分与 postMessage 协议），数据源换成本项目的 `/api/project` `/api/packages/*/components` `/api/scene` `/view`。注意本项目已有 `data-fgui-key` 与 stableKey 体系，直接可当选择主键用。
- **工作量**：中。页面壳是 vanilla JS 拼装（零构建），迁移主要是改数据字段名与包/组件两级树（对方是单级类索引）。

### S2. 全工程 UI 资产索引 + 反向引用查询

对方 `src/scene/ui-asset-index.ts`（245 行）：全工程逐文件三层元数据（基础：class/尺寸/节点数/状态数；结构：组件类型计数/自定义组件/皮肤引用；资源：图片源/位图数字 prefix）+ **解析失败诊断不静默** + findComponentUsages（"谁引用了这个组件"）。

本项目 global-index 只有 pkg -> resources 一层（ui:// 解析够用，但没有"引用关系/使用计数/失败诊断"）。

- **为什么值得**：AI 问"改这个 Button.xml 会影响哪里"时，本项目现在答不上来。
- **同步方式**：以 package.xml + 逐组件 XML 为输入，component 引用边来自 `src` 属性 + loader url，输出引用计数与反向查询。HTTP `/api/ui-assets` + `/api/ui-assets/usage` 两个路由 + MCP 两工具。
- **工作量**：中小。本项目 parser 已产出结构化节点（含 src/url），索引层是纯遍历聚合。

### S3. 组件关系图谱（含图级环检测）

对方 `src/scene/component-graph.ts`（250 行）：引用边三类收集 -> Tarjan SCC 强连通分量环检测（区别于场景级展开环）-> 出入度统计 -> 枢纽排行（被引用最多的组件）-> 孤儿皮肤报告。

- **为什么值得**：本项目 onCycle 只在"单场景展开路径"上检测环；跨分支环（A->B->A 但不在同一展开路径）看不到。枢纽排行对理解工程结构极有用（CC-Default 17 包里 Button/Label 这种被到处引用的枢纽能直接列出）。
- **同步方式**：依赖 S2 的索引做数据源；节点从"类名"换成"包/组件资源 id"。Tarjan SCC 算法部分几乎可原样搬（纯图算法，与引擎无关）。
- **工作量**：中。算法可搬，登记层要按本项目资源模型重写。

### S4. 场景 diff（版本间结构对比）

对方 `src/scene/scene-diff.ts`（241 行）：两份 SceneDocument 的结构 diff。身份两层（id 主键优先 + 同父同类型顺序配对兜底），差异四类（added/removed/moved/changed），changed 到属性级（bounds.x / attrs.text 全量诚实报告）。

- **为什么值得**：AI 改 XML 后回归验证、跨版本 UI 变更审阅，都靠它。本项目改 XML 后只能肉眼看渲染图。
- **同步方式**：本项目 SceneNode 已有 id/name/stableKey/instancePath，身份策略直接套用（FairyGUI 的 id 同样同文件唯一、跨版本保留）。
- **工作量**：中小。

### S5. 语义 HTML -> FairyGUI XML 写出器

对方 `src/writer/exml-writer.ts`（276 行）：渲染产物语义 HTML 回写为 EXML。原则：不猜 DOM->XML 映射，一切结构来自语义属性（data-egret-tag/attrs）；装饰节点（九宫格片/位图位片）跳过；无语义标记报错不静默。

- **为什么值得**：这是"AI 生成 UI -> 落回工程文件"闭环的最后一块。没有它，本项目永远只读。
- **同步方式**：约定 `data-fgui-tag` + `data-fgui-attrs`（原始 XML 属性 JSON 全量）语义标记；写出目标不是单 EXML 而是组件 XML（component/displayList 结构 + 扩展元素 + gear/controller 子元素，比 EXML 复杂，需要拆两期：先纯 displayList 节点，再 gear/controller）。
- **工作量**：大（本项目 XML 形态复杂度约为 EXML 的 2-3 倍）。建议排在 S1-S4 之后独立立项。

### S6. safeResolve 补符号链接复核（小而立即）

对方 `src/assets/safe-path.ts`：前缀检查之外再取 realpath 复核（root 与目标都 realpath，防符号链接穿越 + 规避盘符大小写差异）。

本项目 `src/server/server.ts` 的 safeResolve 只有前缀检查。Windows 下 junction/符号链接场景（前端工程常见）可被穿越。

- **工作量**：半小时级。直接把 25 行守卫搬过来替换，测试补一个越界用例。

### S7. MCP 工具面补齐（跟随 S2-S4 落地）

对方 9 工具 vs 本项目 4 工具。缺的 5 个里：get_node_detail（节点详情，依赖现有 scene-json，可先做）、search_ui_assets + find_component_usages（依赖 S2）、get_component_graph（依赖 S3）、diff_exml_scenes（依赖 S4）、write_exml_from_html（依赖 S5）。

- **同步方式**：逐项跟随底层能力落地，每项 30-50 行薄包装（tools.ts 纯函数与传输层分离的模式本身就值得抄）。

### S8. AI 理解能力 benchmark 方法论（文档级同步）

对方 P4 计划 + benchmark 体系（Gate A 理解 / Gate B 修改两门独立评测、ground-truth 数据集、程序化评分脚本）。本项目未来接 AI 工作台主线时同样需要验收"AI 能否通过 MCP 理解 UI 工程"。

- **同步方式**：不搬代码，把评测框架（两 Gate 设计、题库结构、stableKey 自动核对思路）整理进本项目的需求/规划文档，作为工作台主线的验收方案参考。

## 三、不需要同步的部分

| 项 | 理由 |
|---|---|
| 渲染节点层（bitmapnumber/animation/scroller/rect 等 9 个 node 文件） | 引擎语义差异：Egret 位图数字对应本项目 BMFont（已实现）；动画播放本项目 jta CSS steps 已实现（反而是本项目先做）；scroller/rect 是 EUI 概念 |
| eui-layout 布局引擎 | EUI 的 percent/horizontalCenter 布局体系与 FairyGUI 的 relation 体系不同源，本项目已有 pivot/relation 处理路径 |
| egret-asset-resolver | res.json/json 合图资源协议与 FairyGUI 的 package.xml/图集协议不同 |
| P1 目标组件修复类经验 | GDMahjongMobile 工程特定 |

## 四、反向同步（本项目领先，可回馈对方）

1. **jta 逐帧播放**：对方 animation-node 只有占位（23 行），本项目 CSS steps(1,end) + 负 delay 错帧方案可直接给对方（Egret MovieClip 同样是等间隔帧表）。
2. **经验文档四篇**（server 旧进程/九宫格 fill/九宫格 url 引号/icon 注入遗漏）：对方 CLAUDE.md 只沿袭了规则条目，没有完整踩坑记录，按对方 dev-docs/experience 规范翻译过去。
3. **手动验证指南形态**（12 组件 3 分钟过完的验收路径）：对方 P4 benchmark 走查可用同样形态。
