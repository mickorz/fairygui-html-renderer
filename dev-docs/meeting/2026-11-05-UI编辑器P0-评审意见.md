## 二、评审最认可的 5 个技术决策

1. **GrapesJS 默认配置三个坑被真正解决**（最有价值发现）：`avoidInlineStyle:false + forceClass:false + protectedCss:"" + selectorManager:{componentFirst:true, appendTo:""}` 五配置组合；五样本 semantic/geometry/asset 差异全零。应沉淀为项目长期技术规范。
2. **拖动按需提升而非强制绝对定位**：拖动开始记录原始布局、结束时检查 static→absolute 才标记、保留快照、Undo 可恢复；测试覆盖普通/flex 静态子元素/嵌套/滚动容器/画布缩放。方向正确。
3. **React 与 GrapesJS 职责边界**：React（工具栏/图层/属性面板/状态栏）→ 外部 Store（`useSyncExternalStore`）→ GrapesJS → 画布 DOM。避免双框架争抢 DOM；**建议 P1 不为方便打破边界**。
4. **Session 保存机制完整**：source / editor / project.json / assets / output 分层 + `sourceRevision` 乐观锁；与既定本地工作区方案一致。
5. **Converter 未被编辑器污染**：经临时 HTML + `<link>` 注入复用原 `runPipeline`，未新写转换逻辑；**UI 编辑器是独立能力，未来替换 GrapesJS 不应影响 Converter，必须保持**。

## 三、评审发现的 4 个遗留问题（P0 收尾清单来源）

### 问题 1：真实 FairyGUI 编辑器验收未完成（待人工验收）

已完成：编辑 HTML → GrapesJS 导出 → Converter 生成 XML → Renderer 回读。
还缺：生成 XML → 打开真实 FairyGUI Editor → 检查组件与资源（GButton 是否仍可编辑、GTextField、图片与 Package 资源关联、九宫格/字体/组件层级）→ 修改组件 → 保存工程。**不能用 Renderer 回读代替。**

### 问题 2：未用真实 AI 生成的 HTML 做保真度测试（待补充样本）

现有五样本为人工制作。真实 AI HTML 可能含更多层级嵌套/复杂 CSS/图片背景/复杂文字排版/不同定位方式/SVG 特殊资源。**建议补 3～5 个真实 AI UI 到 `tests/fixtures/editor/` 作为长期回归样本。**

### 问题 3：滚动容器拖动后 GrapesJS 内部状态残留

`_cmpDrag` 等状态在 Playwright 合成事件下可能残留，当前测试以 reload 规避。暂不改 GrapesJS 源码，**P1 应解决真实交互的状态清理**（滚动容器拖动 → 画布拖动 → 点击 → 继续拖动的连续序列不得出现选中失效或坐标漂移）。

### 问题 4：部分 UI 功能未接线

`TopToolbar.tsx` 中保存/Undo/Redo/Zoom 已接通，**Preview 与 Export 暂时禁用**；服务端 POST convert 已实现但前端无转换操作入口。不影响 P0 结论，实际使用前需在 P0 收尾或 P1 补齐。

## 六、P1 优先级调整：语义映射优先于通用编辑功能

结合最终目标（AI 生成 UI → 人工调整 → FairyGUI），P1 最重要的不是继续完善通用编辑器功能，而是**建立 HTML 元素与 FairyGUI 组件的语义映射**：

| HTML 元素 | FairyGUI 组件 |
|-----------|---------------|
| 普通容器 | GComponent |
| 图片 | GImage |
| 文本 | GTextField |
| 按钮 | GButton |
| 列表 | GList |
| 装载器 | GLoader |
| 控制器关联节点 | Controller / Page |

建议引入轻量语义属性（如 `data-fgui-type="GButton"`，配合已有 `data-fgui-node-id`）：不是让 HTML 直接变 XML，而是让节点拥有稳定的 FairyGUI 语义。收益：

- AI 可生成带明确组件语义的 HTML；
- 编辑器可按语义显示不同属性面板；
- Converter 可按语义选择转换规则；
- AI 可知道当前选中的是按钮还是容器。

对 AI 游戏 UI 工作台而言，这比增加更多 CSS 编辑属性更有价值。
