# GrapesJS 滚动容器内拖动后 sorter 状态残留污染下一次拖动

## 问题现象

自动化测试（Playwright）中连续两次拖动：第一次拖动发生在**滚动容器内**（`overflow:auto` 的父容器，已滚
动过 scrollTop），第二次拖动画布内普通 absolute 元素时结果异常——位移量既不等于屏幕位移，也不等于
任何已知换算值（本例期望 +40/+20，实际 +45/+20；另一场景为 +56/+30），且结果确定性复现。

而「滚动容器拖动」本身结果正确（left/top 相对内容坐标，滚动量未混入）。

## 排查过程

1. 孤立探针（干净页面、单个元素、zoom 100%）连续拖动两次：两次结果均精确——排除「连续拖动」本身；
2. 孤立探针 zoom 50% 下拖动：设计位移 = 屏幕位移 / zoom，精确成立——排除 zoom 换算缺陷；
3. 对照差异：出问题的用例中，前一用例是「滚动容器内拖动」。重载页面后再做同一次拖动（相同坐标、相同
   步长）→ 结果立即精确。

结论：滚动容器内的拖动结束后，GrapesJS 内部 sorter/dragger 状态有残留，污染紧随其后的下一次拖动
的起始位置计算（delta 从残留的旧起点算起，所以是无规律偏差）。

## 根因

与 Task 3 记录的 `_cmpDrag` 残留（`grapesjs-cmpdrag-synthetic-event-residue.md`）同族：真实浏览器里
拖动结束靠 trailing click 清理状态；Playwright 合成 mouseup 被 preventDefault 后，部分清理路径不走，
滚动容器路径下残留的不止 `_cmpDrag` 一个标志位（sorter 起点等），单清 `_cmpDrag` 不够。

## 解决方案

自动化测试层面规避（P0 结论，未深入 GrapesJS 内部修复）：

- **涉及滚动容器拖动的用例之后，若还要继续拖动断言，先 `page.reload()` 重载页面取干净状态**，再
  `__editorLoad` 恢复样本；
- zoom 换算验证（drag-check 用例 6）即采用该方式：重载 + setZoom(50) + 拖动，结果精确（y 轴精确命中，
  x 轴落在 5px 吸附栅格）。

另注意两点：

- **zoom 换算公式本身正确**：设计位移 = 屏幕位移 / zoom（zoom 50% 时 ×2），孤立验证精确成立，无需修
  GrapesJS；
- **Dragger 有内建 5px 吸附栅格**，命令链不可配置（Task 3 已记录）。zoom 下步长为分数（屏幕步长/zoom）
  时最终落点可能吸附到相邻栅格（80 与 85 之差），换算类断言按 ±5px 容差判定，验证目标是换算系数而非
  亚像素精度。

## 预防/注意事项

- 测试脚本中滚动容器拖动用例尽量放在拖动断言序列最后，或其后立即重载页面；
- 「拖动结果无规律偏移」这类问题，先怀疑前一次交互的编辑器残留状态（reload 隔离验证是最快的二分手
  段），再怀疑换算逻辑；
- 截图/坐标断言里 iframe 内元素 rect 是 iframe 视口坐标（不随外层 CSS 缩放），换算屏幕坐标要乘
  zoom（见 drag-check pagePoint 实现）。
